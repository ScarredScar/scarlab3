# Лабораторная работа №7. Ответы на контрольный вопрос

## Контрольный вопрос: почему SendMessage блокирует отправителя?

Оба вызова — `PostMessage` и `SendMessage` — приводят к одному и тому же результату: приёмник получает сообщение `WM_USER+1337` с параметром `777` и завершается. Однако на низком уровне логика работы процессора и ядра Windows у них принципиально разная.

### PostMessage — асинхронная отправка

`PostMessage` **не ждёт** обработки сообщения:

1. Поток-отправитель формирует структуру `MSG` (HWND получателя, код сообщения, WPARAM, LPARAM).
2. Делает системный вызов, попадает в Ring 0 (подсистема `win32k.sys`).
3. Ядро Windows находит в своей внутренней таблице **очередь сообщений потока-получателя** (каждый GUI-поток имеет свою очередь).
4. Ядро **добавляет** структуру `MSG` в конец этой очереди и **сразу возвращает управление** отправителю.
5. Отправитель продолжает работать. Он **не знает**, когда и как получатель обработает сообщение.

В нашем эксперименте это видно по выводу отправителя:

```
[ОТПРАВИТЕЛЬ] Вызываем PostMessage: отправляем асинхронный сигнал 777...
[ОТПРАВИТЕЛЬ] Сообщение успешно сброшено в очередь Windows. Конец работы.
```

Строка «Конец работы» появляется **сразу**, ещё до того, как приёмник реально получил и обработал сообщение.

### SendMessage — синхронная отправка

`SendMessage` **блокирует** поток-отправитель до тех пор, пока получатель не обработает сообщение:

1. Поток-отправитель формирует структуру `MSG`.
2. Делает системный вызов, попадает в Ring 0.
3. Ядро Windows определяет, **какому потоку** принадлежит окно-получатель (`HWND → Thread ID`).
4. Если это **другой поток** (как в нашем случае — разные процессы), ядро **не кладёт сообщение в очередь**, а **напрямую вызывает оконную процедуру получателя** (`WndProc`) в контексте потока-получателя.
5. Ядро **переключает контекст** на поток-получатель и заставляет его выполнить `window_procedure(hwnd, WM_MY_COMMAND, 777, 0)`.
6. Пока получатель не вернёт результат из `WndProc`, поток-отправитель находится в состоянии **`Waiting`** — он не получает кванты времени от планировщика Windows.
7. Только после того, как `WndProc` вернёт управление, ядро разблокирует отправителя и вернёт результат вызова `SendMessage`.

В нашем эксперименте это видно по выводу отправителя:

```
[ОТПРАВИТЕЛЬ] Вызываем SendMessage: отправляем синхронный сигнал 777...
[ОТПРАВИТЕЛЬ] Сообщение обработано получателем. Конец работы.
```

Строка «Конец работы» появляется **только после того**, как приёмник получил сообщение и завершился.

## Что происходит с контекстом регистров потока-отправителя

Когда `SendMessage` вызывается, происходит следующее:

1. **Сохранение контекста.** Ядро Windows сохраняет **полный контекст** текущего потока-отправителя:
   - регистры общего назначения (`RAX`, `RBX`, `RCX`, `RDX`, `RSI`, `RDI`, `R8`–`R15`),
   - указатель стека (`RSP`), указатель базы (`RBP`),
   - регистр флагов (`RFLAGS`),
   - регистр инструкций (`RIP`) — адрес возврата в коде отправителя.

   Всё это сохраняется в структуре **`KTHREAD`** (объект ядра, описывающий поток) — точнее, в её части **`KTRAP_FRAME`**.

2. **Переключение стека.** Поток-отправитель полностью снимается с процессорного ядра. Планировщик Windows выбирает следующий поток для выполнения — им становится **поток-получатель**.

3. **Поток-отправитель помещается в состояние `Waiting`** с указанием, **какого события он ждёт** — завершения обработки сообщения в `WndProc` получателя.

4. **Поток-получатель исполняет `WndProc`** в своём контексте. Регистры его собственные, стек свой. Он обрабатывает сообщение, возвращает код.

5. **Возврат управления.** Когда `WndProc` завершён, ядро:
   - помечает поток-отправитель как готовый к выполнению (`Ready`),
   - восстанавливает **сохранённый контекст** регистров отправителя из `KTRAP_FRAME`,
   - продолжает выполнение ровно с той инструкции, которая шла после `SendMessage`.

**Что находилось в регистрах в момент вызова:**

В регистрах отправителя в момент вызова `SendMessage` находились:
- **`RIP`** — адрес инструкции, следующей за точкой вызова `SendMessage`. Именно сюда ядро вернётся после разблокировки.
- **`RSP`** — указатель на стек отправителя. Ядро сохранило его, чтобы восстановить стек при возврате.
- **`RAX`/`RDX`/`RCX`** — рабочие значения отправителя, которые **сохраняются и восстанавливаются** после обработки.
- **`RFLAGS`** — флаги состояния процессора.

Именно эти сохранённые значения и восстанавливаются, когда `SendMessage` возвращает управление. Поэтому с точки зрения программиста на Python вызов выглядит как «обычная функция»: строки после `SendMessage` выполняются только тогда, когда получатель уже отработал.

## Итог

| Критерий | PostMessage | SendMessage |
|---|---|---|
| Тип вызова | Асинхронный | Синхронный |
| Что делает ядро | Кладёт `MSG` в очередь получателя | Прямо вызывает `WndProc` получателя |
| Состояние отправителя | Продолжает работу | Ждёт (`Waiting`) |
| Когда завершается отправитель | Сразу после syscall | После возврата из `WndProc` |
| Контекст регистров отправителя | Не меняется | Сохраняется и восстанавливается |
| Межпроцессное взаимодействие | Возможно | Возможно (с блокировкой) |

`SendMessage` блокирует отправителя потому, что он **не использует очередь**. Вместо этого ядро Windows организует **прямой синхронный вызов чужого `WndProc`** в контексте потока-получателя, а поток-отправитель переводит в состояние `Waiting` до момента возврата результата. Это даёт гарантию, что сообщение обработано, но лишает отправителя возможности продолжать работу параллельно.
